# 리펙토링

## 비즈니스 로직을 수정

- [x] Title, Tags, Nickname 모델과 테스트 코드를 삭제하고 BoardData, Tag 두 개의 모델로 리펙토링 했습니다.
    - 크롱의 피드백처럼 Tag의 maxTagLength와 Tags의 maxTagsSize를 UI와 모델 중에 어디에 있어야할까? 라는 질문에서 시작됐습니다. 가장 최근에 고친
      코드에서는 maxTagLength와 maxTagsSize를 검증하는 코드를 UI에 위치시켰습니다. 하지만 그렇게 된다면 UI가 검증과 그리기를 동시에 하게 됩니다. 이런
      방식은 문제라고 생각했고 어디서부터 잘못된 것인지 코드를 뜯어볼 수 없어서 수업 때 배운 TDD를 활용해 비즈니스 로직을 다시 설계했습니다.
    - BoardData.kt
        - 기존 코드와 달라진 점은 title, nickname과 같은 값에 대한 객체를 만들지 않고, boardData라는 큰 비즈니스 로직을 설계했습니다. 또한
          Tags라는 객체보다 Tag를 가지고 있는 리스트를 Tags로 받는다면, Tag 객체에서 최대 길이에 대한 조건을 가지고 Tag를 가지고 있는 리스트에 대한
          조건을 boardData가 가질 수 있도록 했습니다.
    - Tag.kt
        - Tags라는 객체보다 Tag를 가지고 있는 리스트를 보내는 것이 좋다고 생각해서 Tag라는 객체를 설계하게 되었습니다.

## UI 로직을 수정

- [x] 변경한 비즈니스 로직을 기반으로 전체적으로 수정함
- [x] 자식 컴포넌트들은 stateless로 바꾸기 위해 노력했습니다.
    - stateless로 변경한 이유는 비즈니스 로직과 UI 로직을 구분하기 위해서 한 작업이기도 합니다. 지금 문제라고 생각하는 부분은 UI로직과 비즈니스 로직을 제대로
      나누지 못한 점인데, 이는 다르게 보면 자식 컴포넌트가 stateful이기 때문에 구분이 어려워진게 아닐까? 라는 생각이 들었습니다. stateless로 변경하는
      과정에서 상태를 관리하는 로직을 전부 위로 올리게 되면서 의문을 품었던 생성 버튼에서 검증하는게 맞을까? 또는 텍스트 필드에서 검증하는게 맞을까? 에 대한 답을 찾은 것
      같습니다. 상태 호이스팅을 통해 검증 로직을 위로 올리게 된다면 버튼(자식 컴포넌트)이 검증하는 것이 아니라 위에 있는 검증 로직을 전달하는 방식이 되며 버튼(자식
      컴포넌트)이 갖는 책임을 줄일 수 있게 된다고 생각했습니다.

## 테스트 코드를 수정

- [x] 비즈니스 로직의 경우 TDD를 활용해 작성하였습니다.
- [x] UI 테스트의 경우 단위별로 나눠놓은 컴포넌트를 활용해서 할 수 있는한 가장 작은 단위 테스트로 나눠서 UI 테스트를 진행했습니다.

### BoardDataTest 시나리오

- 태스크는 제목, 설명, 태그, 상태, 담당자를 가진다
- 제목이 빈 문자열이면 태스크 생성이 불가능하다

### TagTest 시나리오

- 태그는 최대 5개까지 생성 가능하다
- 태그는 5글자까지만 가능하다
- 태그는 5글자를 초과하면 오류가 발생한다
- 태그에 공백이 들어가있으면 오류가 발생한다

### DialogTest 시나리오

- 상태 버튼을 클릭 했을 때 버튼 인덱스가 변경된다
- 담당자 버튼을 클릭 했을 때 버튼 인덱스가 변경된다
- 텍스트 필드에 입력한 내용이 입력한대로 출력되어야 한다
- 제목 검증 실패시 에러 표시가 출력되야 한다
- 태그 검증 실패시 에러 표시가 출력되야 한다
- 제목 검증 혹은 태그 검증에 실패시 생성 버튼 비활성화 되어야 한다
- 제목 검증 혹은 태그 검증에 성공하면 생성 버튼이 활성화 되어야 한다
